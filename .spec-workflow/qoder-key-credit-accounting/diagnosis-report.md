# Key 用量统计根因与验证

日期：2026-10-12。实现基线：main / 0f8ed49。

## 现象与确认口径

用户提供的 Key 列表与限制弹窗对同一账号显示不同已用量。用户最终明确：列表采用本 Key 的已用 N / 当前最新分配额度；不采用账号完整套餐额度，不随账号充值自动改变 Key 分配。

前期“CC-SWITCH 将 used 错当余额”的判断没有消费方证据，已撤回。接口字段维持 used=已用、balance/remaining=剩余，不能用互换字段掩盖统计问题。

## 代码已复现的根因

1. 额度弹窗采用 max(账号原始剩余-当前剩余, ledger.used)。共享账号由其它 Key 或其它客户端产生的消耗被归入当前 Key，与 CC-SWITCH 精确 ledger 不一致。
2. evaluateApiKeyProviderCreditUsage 在找到第一可用优先账号时 break，漏算后续账号用量；又裁剪到每个账号预算，隐藏真实超额扣费。
3. 配置校验只有上限，没有禁止下调到已用量以下；其它 Key 的预留也未减去其已消耗部分。
4. Key PUT 在网络查询前读取 ledger，查询后使用旧 ledger 覆盖整份 policy，可能丢失编辑/查询期间的并发扣费。其它管理员同时分配也需要在同一写事务内复核预留。
5. 读取账号余额的 merge ledger 仍能通过历史 baseline/余额下降增加非 precise Key 的用量；周期充值和共享消耗无法据此归属。
6. CC-SWITCH 对已分配 Key 的查询等待所有上游额度返回，尽管 Key 分配余额可直接从自身账本计算。

## 失败复现

命令：npx vitest run --config tests/vitest.config.js --pool=threads --maxWorkers=1 tests/unit/qoder-key-credit-accounting.test.js

修复前 3 failed：双账号应 used=1900，实际=1200；已有 1200 却下调到 1000，实际保存校验通过；共享账号 B 应只预留 1300，实际预留2000，且 Key 消耗被账号余额下降放大。

## 修复范围

运行时鉴权、后台列表统计、弹窗预览、CC-SWITCH 全部使用自身持久化账本；merge 只更新观测检查点不推断扣费。现有 evaluator 的显式历史 baseline 诊断能力保留以兼容旧纯函数调用，所有生产调用明确关闭 useBaselineFallback。

新分配、优先级、充值不清零；配置修改后 total 为最新分配值。下限为已用，上限为已用 + max(0, 账号余额 - 其它 Key 剩余预留)。SQL 事务内复核最新用量和其它 Key 的配置，合并当前 ledger，保留并发扣费和历史记录。

已分配 Key 的两个余额接口直接返回本地账本；未分配 Key 的查询继续读取允许账号的上游余额，采用既有超时/并发控制。

## 清理、局限与后续

未添加生产调试日志；没有提交、推送、部署或生产数据变更。隔离浏览器服务已停止，成功运行的测试临时数据库已清理。首次失败测试的临时数据库删除被自动审批拒绝（blocked by policy），改为可恢复移动至 debug/failed-browser-database/，约36KB，作为调试材料保留。debug/ 下另保留浏览器复测脚本和上游 fixture，verification/ 下保留截图及本地服务日志，供验收复跑，不应作为生产源码部署。

旧数据中缺少精确 credits 的请求无法仅凭账号余额下降分配到 Key；保留已有 ledger 作为历史记录，本轮不自动重算历史生产账目。若用户要求校准旧账，需以能够归属 Key 的完整请求证据进行单独数据修复，不能将资源包总消耗强行归给单个 Key。

账户余额查询是某一时刻的上游快照；事务可避免本站其它 Key 的同时配置造成重复预留，但无法锁住 Qoder 官网或其它客户端正在发生的消费。历史诊断 fallback 可在后续移除，以降低未来新调用误启用的风险。
